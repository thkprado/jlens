## Priorities

Three principles order the work after 0.2:

1. **The core is a library for custom integrations.** Applications embed `jlens-core` in their
   own pipelines. It must stay small and decoupled, let the application set every limit, never
   panic, and change its API only on purpose.
2. **The CLI is a tool for automation and AI agents.** It never prompts, it gives the same
   output for the same input, and it has one documented machine-readable contract: what goes to
   standard output, what goes to standard error, and what each exit code means.
3. **Editors come after.** The language server is done; the VS Code extension is 0.15.

For ad-hoc JSON queries, `jq` remains the usual tool. jlens is for JSONata that will run
somewhere else, such as a rules engine or a jsonata-js service. It checks those expressions,
tests them and explains their results before they ship.

## 0.11: faster evaluation of common shapes

A comparison with [jsonata-core](https://github.com/txjmb/jsonata-core) 2.2.11, another Rust
port, on the cases of `benches/` (`evaluate_document` against its `evaluate`, both converting the
result to `serde_json::Value`) found it 2 to 5 times faster on five cases: path (0.9 against
0.1 µs), filter + aggregate (164 against 93 µs), group-by (570 against 123 µs), sort + map
(1.79 ms against 655 µs) and the shipping rule (433 against 254 µs). Both engines are about
equal on the other cases, and jlens is faster on regex. Measuring
parts of these expressions traced the gaps to a few places in `eval.rs`, where work is repeated
or allocated that no result depends on. Each item removes one of them without changing any
result, error or evaluation order that jsonata-js shows. jsonata-core's other technique, a
second evaluator for simple expressions, is left out: two evaluators of the same language can
disagree.

Every item is measured with `cargo xtask ab` against the commit before it, and checked with the
conformance suite and a `cargo xtask differential` run. When a tracer is attached, evaluation
takes the general path, so audits keep reporting every node.

| # | Deliverable | Definition of done | Status |
|---|---|---|---|
| 1 | Sort keys are evaluated once per item. The order-by operator (`^(...)`) evaluates the keys of both items at every comparison, as jsonata-js does: about 3,000 evaluations to sort 200 items, where 200 suffice. `items^(tax)` takes 1.05 ms, against 208 µs in jsonata-core | Each item's keys computed on first use and kept, so the keys are evaluated in the same order and the first error is the same; tests for `T2007` and `T2008`; sort + map faster with `ab`; the compatibility page notes that a key using `$random` is drawn once per item | **done** |
| 2 | A block without a binding creates no frame. `(...)` allocates a frame each time it is evaluated, so `items.(unitPrice)` takes 85 µs where `items.unitPrice` takes 16 µs | Post-processing marks the blocks whose own expressions bind a variable (`:=`), and only those create a frame; tests for scoping and for closures defined in a block; `ab` | **done**: `items.(unitPrice)` 83 → 77 µs; the rest of the gap is the one-step path of #3. A block that calls a function keeps its frame when the expression names `$eval`, which binds in its caller's frame |
| 3 | A field name evaluated on an object is a lookup. A bare name such as `unitPrice` is a path of one step, which builds and flattens sequences: about five allocations per evaluation. `items.(unitPrice * quantity)` takes 159 µs, against 39 µs in jsonata-core | A one-step path of a name, without stages, on an input that is not an array, returns the field when its value is not an array, and takes the general path otherwise; unit tests for the sequence and singleton rules it skips; filter + aggregate, group-by and the shipping rule faster with `ab` | **done**: filter + aggregate 161 → 56 µs, group-by 842 → 575 µs, shipping rule 414 → 152 µs, strings 198 → 104 µs (`ab --mode document`); a property test checks that evaluation agrees with an audit, which takes the general path |
| 4 | A string literal does not allocate each time it is evaluated. Today it builds a new `Rc<str>`, so `items[type = 'electronic']` allocates one string per item. Exploration: a string shared by the evaluation, or a comparison with the literal that builds no value | The allocation gone and measured with `ab`, or the cost and the options recorded on the performance page | **done**: `=` and `!=` compare with the literal's text, untraced: filter + aggregate 56 → 44 µs, strings 105 → 92 µs, shipping rule 150 → 127 µs (`ab --mode document`). Other uses (arguments, `&`, object values) still build a string: sharing one per evaluation needs a slot per literal, since the AST is `Send` and values use `Rc` |
| 5 | The result is converted in one pass. | 6 | The fixed cost of an evaluation is cut. `1` takes 0.35 µs, against 0.07 µs in jsonata-core: the clock is read twice for `$now` and the seed of `$random`, and the root frame and the binding of `$` allocate | The clock read once, and only what an evaluation uses set up; the path case faster with `ab` | **done**: the clock is read on first use, the start time only with a timeout, and the input is kept in the root frame instead of a binding of `$`: `1` 350 → 106 ns, path 927 → 676 ns (`ab --mode document`) |
| 7 | The performance page shows the new numbers, natively and in WebAssembly, with the comparison with jsonata-js | The tables measured again; the "Where the time goes" section updated | **done**: natively, `evaluate_document` is 2 to 4 times faster than in 0.8 on filter + aggregate, sort + map and the shipping rule; jlens-wasm `evaluateDocument` is now faster than jsonata-js on all ten cases |

## 0.12: jlens online

Today the book and the web editor exist only in the repository: the README links no site, CI
builds the book only to check it, and trying the editor takes a clone, a Rust toolchain and
`cargo xtask wasm`. This release publishes both on GitHub Pages, at each release tag, as
[try.jsonata.org](https://try.jsonata.org) does for jsonata-js. The editor shows what sets
jlens apart (completion from an inferred schema, diagnostics, the explanation and audit tree of
every result), and everything runs in the browser: no expression or document leaves the
visitor's machine.

The site is the book at the root and the editor under `editor/`, built from the files of the
tag, so the editor runs the engine that the book of that version describes. The first
deployment, and enabling Pages in the repository settings, wait for the maintainer.

## 0.13: host functions that call back

A host function cannot call a JSONata function it receives as an argument: the argument arrives
as `None` (`undefined` in WebAssembly), as ADR 0006 decided. Rule engines need it for helpers
written in the host language that apply a function given to them (`$retry($fetch, 3)`,
`$memoize(function($k) {...})`, a lookup with a fallback function). This release adds a
callable handle without changing the functions already written against ADR 0006.

| # | Deliverable | Definition of done | Status |
|---|---|---|---|
| 1 | The design, in ADR 0011. ## 0.18: the fields an expression reads

An application that evaluates rules builds their input first, often from a database or a
service. Knowing which fields a rule reads, it could fetch only those; it could also show which
rules depend on a field. jlens can answer from the expression alone: `$sum(items.quantity)`
reads `quantity` in each item of `items`, and nothing else. The answers of several rules
evaluated on the same input combine: their union is what all of them read. The same answer, for
one rule or their union, lets jlens skip, when it parses JSON text, the fields no evaluation
will read.

JSONata is dynamic, so the answer is an upper bound. Where the analysis cannot follow, it says
that a value is read whole: the wildcards `*` and `**`, `$keys`, `$each`, `$sift`, `$spread`,
`$string`, `$lookup` with a computed key, `$eval`, a value passed to a host function, a
transform or a lambda other than one written as the argument of `$map`, `$filter`, `$single`,
`$sort` or `$reduce`, an object in the result. For the paths,
comparisons and aggregations rules are mostly made of, it is exact. A wrong answer would not
fail: a field left out reads as undefined and the rule gives another result. So the test is the
suite: each case evaluated on its input cut down to the fields reported must give the same
result as on the whole input.

## 0.19: closing on jsonatapy

With Python values in, `jsonatapy` is still faster than jlens on four of the twelve cases of
`benches/compare/python.py`, measured again on 0.18.0 (WSL, Python 3.14.8): `path` (1.1 against
0.7 µs), `names over items` (38 against 26 µs), number formatting (169 against 161 µs) and the
object constructor (367 against 195 µs). Timing variants of each case and profiling them with
`perf` found three causes:

- **Converting the result.** Without its result converted, the object constructor evaluates
  faster in jlens: `$count(items.{...})` takes 155 µs against a `Document`, 177 µs in
  `jsonatapy`. Converting the 200 objects to `dict`s then costs jlens about 138 µs. A result
  is converted twice, into a `serde_json::Value` (`Value::to_json_spending`, a map with
  SipHash keys) and then into Python objects, with a new `str` for each key of each `dict`. A
  string of the result costs 90 ns, against 24 ns.
- **Reading an array of objects.** Each `dict` of a `list` that the evaluation does not read
  costs 98 ns, against 30 ns: `$count(items)` takes 20 against 6.5 µs. About 40% of it is
  `malloc` and `free`, since each item allocates twice, its boxed source and its `Rc<Object>`.
  Looking a field up in the `dict` costs the same in both.
- **The evaluator.** A predicate is evaluated once per item even when it does not depend on
  the item: `[[0..19]]` builds the range 200 times, and `$count(items[[0..19]])` takes 87 µs.
  An object constructor goes through grouping even for a single item: `$count(items.{'kind':
  'item'})` takes 73 against 40 µs. `$formatNumber` takes 2.7 µs a call, against 1.8 µs.

On `path`, the gap is mostly a fixed 0.24 µs that Python values add to each evaluation. Each
item measures the cases it touches before and after with `cargo xtask ab`, plus
`python.py speed` when the Python package is concerned.

## 0.20: a deterministic step limit

An application that evaluates expressions written by others needs a ceiling on what one
evaluation may cost. jlens has three, and none is both general and reproducible. `max_depth`
stops a deep recursion (`D1011`) and the size limits stop a huge value (`U1001`), the same way
on every machine, but loops over small arrays nested a few times pass both:
`$sum($map([1..1000], function($i) { $sum($map([1..1000], function($j) { $i * $j })) }))`
builds no array longer than 1,000 items. Only the timeout (`D1012`) stops them, and the timeout
reads the clock: the same expression on the same input passes on a fast machine and fails on a
slow one, or passes natively and fails in WebAssembly, which is slower. An application that must give the
same answer everywhere, such as a replay, a test that compares two platforms or a quota charged
to a user, cannot rely on it. Today's workaround, a tracer that counts `enter` events and
cancels a `CancelToken`, forces the traced evaluation, which is slower.

0.20 adds `Options::max_steps`, a budget of evaluation steps that fails with its own code once
spent. The same expression, input and options take the same number of steps on every machine,
natively and in WebAssembly, with or without a tracer.

Measured while planning, with a prototype that decrements a counter at each step (`u64::MAX`
without a limit, so there is no branch on an `Option`): `cargo xtask ab` found every case
between 3.4% faster and 1.3% slower than `HEAD`, which is noise; with a limit set, the code path
is the same. The prototype also showed a cost the counter can remove. With a timeout, every step
reads the clock: `$sum($map([1..300000], function($x) { $x * 2 + 1 }))` takes 189 ms with
`jlens eval --timeout` against 127 to 153 ms without (Windows). Reading the clock every few
hundred steps would remove most of that cost.

## 0.21: documents built from Rust values

An application that keeps its state in Rust types and evaluates against it has one way to get a
`Document`: build a `serde_json::Value` and convert it with `Document::new`. When the document is
rebuilt often, from a state that changes between a few evaluations, that double conversion costs
more than the evaluations. One application measured it, rebuilding a document of about 10
objects of 20 fields and evaluating it 1 to 10 times: building the `serde_json::Value` took
35–40% of its time, `Document::new` 15–18%, the evaluations much less than both. Binding one of
those objects to a variable of `evaluate_document` made the whole 8–14% slower, as the variable
is converted whole at every evaluation.

Measured while planning, with a prototype of `Document::from_serialize` and the benchmark
`crates/jlens-core/benches/host_state.rs` (ten records of twenty fields, rebuilt at each
iteration, then 1, 4 or 10 small expressions; Windows): building the document takes 43.7 µs
through `to_value` and `Document::new`, 35.8 µs through `to_string` and `Document::parse`, and
17.9 µs serialized straight into it; building and evaluating, 43.0 → 19.3 µs with one
expression and 72.1 → 48.7 µs with ten. A record read through a variable takes 3.5 µs, read from
the document 1.0 µs. [ADR 0019](../adr/0019-documents-from-rust-values.md) has the whole table.

## 0.24: reading the application's values faster

does not parse itself, and two of the costs it found belong to `jlens-core`, so they reach
every package.

- An index into an array, such as `items[0]`, copied the whole array first: 2.6 ms on 100,000

## 0.25: a Java package

JSONata on the JVM has jsonata-java and JSONata4Java. [ADR 0021](../adr/0021-java-package.md)
puts jlens there through a C API that Java 25 calls with Panama, after a spike that measured it
against jsonata-java. On a `Document`, jlens was 2.6 to 70 times faster. On JSON text it was
1.2 to 2.7 times faster, and 1.8 to 2.5 times on 16 threads or 1,000 virtual threads. The
package follows the Python and WebAssembly ones: the same objects, the same errors, beta until
1.0. It ships before the API work, as they did ([ADR 0021, amended](../adr/0021-java-package.md#amendment-before-the-api-work-2026-10-25)).
The spike's code is the starting point, not the package: the decisions are in the ADR.

The C API comes first, in two parts, then the Java API over it, then a benchmark in the
repository, so that every later item is measured with the same harness. The Java source reads
what 0.17 and 0.24 taught the Python one to read: one field, one item, or one level.

## In exploration: a regular expression engine of jlens's own

`jlens-regress` is a backtracker. A catastrophic pattern runs within the evaluation's limits
([ADR 0009](../adr/0009-bounded-regex.md)), but it still runs to them. Its positions are code
points, which jlens converts to UTF-16. On the engine's benchmark, V8 is 2 to 11 times faster.

An engine of jlens's own could find a match in linear time wherever the pattern allows it: an
automaton finds the match, and the backtracker is left only to extract its groups, or to run
the patterns that need it (backreferences, lookarounds). It would also have the interrupt and
UTF-16 positions built in, with no `unsafe`.

This is research, not a release. The work lives apart from `jlens-core`, and the corpus, the
differential test and the benchmark of 0.22 measure it. It ends in a decision: an ADR that adopts
the engine in place of `jlens-regress`, or drops it. Adopted, the swap becomes a release of its
own.

## Deferred: an API to keep, toward 1.0

After twenty releases, nothing says which parts of jlens are meant to last. `cargo
semver-checks` runs in CI, but before 1.0 it only asks for a new minor version, and
`jlens-core` exposes workspace plumbing (`stack`, `debug`, the AST's internals) next to its API.
This work decides what 1.0 will promise, breaks the API once to get there, and writes the
promise down. It takes the number of the next release when it starts. Applications built on jlens are separate projects: they use `jlens-core` as any
application does, and what they lack comes back here as general features.

**Deferred** until applications built on jlens have used it: what to keep stable is decided
from what they needed, missed or worked around, not guessed beforehand.

## Not planned

- **Asynchronous functions.** A host function that returns a promise fails with `U1002`, and
  jlens does not plan to change that. Supporting it needs an evaluator that can suspend, which
  would slow down every evaluation, and only WebAssembly would gain from it: a Rust host
  function can block. An application can fetch what its functions need before evaluating.
  Should real use call for it, the cheaper way is an `evaluateAsync` that stops at the first
  promise, awaits the pending ones and evaluates again with their results.
